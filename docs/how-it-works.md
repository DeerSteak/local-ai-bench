## Execution order

With no wrapper arguments, `run_bench.sh`/`run_bench.bat` uses `benchmark_launcher.py` to select the Tk GUI on a usable local desktop or the terminal frontend over SSH/headless sessions. `--ui` can force GUI, terminal, or noninteractive operation. Both interactive frontends launch `benchmark.py` as a child process with explicit CLI flags — see [Launch modes](cli-reference.md#launch-modes). The frontends never call benchmark orchestration directly; ordinary benchmark arguments bypass them and forward straight to `benchmark.py`, which is always non-interactive.

Before its first GUI-launched run, `benchmark_gui.py` uses existing read-only inventory and platform probes to show runtime/model readiness. These probes do not start a server or call setup; the existing frontend state file records the first successfully launched selection so onboarding does not require a second persistence mechanism.

For GUI-supervised runs only, the launcher sets `LOCAL_AI_BENCH_PROGRESS=1`. Stage orchestration and the workload model loops then emit small private JSON lifecycle markers that the always-on-top Tk progress window consumes and removes from the detailed log. Supervised worker output relays these markers without timestamp decoration so each model transition remains machine-readable; without that environment variable, CLI output is unchanged.

Before profiling hardware or creating an output path, the CLI expands test groups, applies `--maxtier`, resolves the LLM/embedding/image selectors, and performs a validation-only pre-pass for every selected engine. Local inventory is read only when custom LLM matching or concurrency scoping needs it; no model is loaded and no inference server is started. An explicit selector that leaves one of its selected workload families empty aborts the invocation at this point. With `--engine all`, every engine must validate before any runs; the resolved scopes are cached so hardware profiling and the filename timestamp still happen once and all per-engine files share the same stem.

`--list-models` uses the same read-only inventory helpers and exits before profiling. It reports catalog LLMs, embeddings, custom LLM folders, and catalog image checkpoints from Local AI Bench's managed `models/comfyui/` directory; the resolved `--comfyui` path selects the program used to run those models, not their storage location.

Selected tests run in a fixed stage order, independent of the order passed to `--tests`:

```
single-shot LLM (all selected models, xsmall → large)
  → conversation LLM (all eligible selected models)
  → llama-bench (opt-in)
  → llama-bench concurrency (opt-in)
  → embeddings
  → accuracy (MCQ → math → reasoning → code → tool)
  → concurrency (tool → chat)
  → images
```

See [Engines](engines.md) for `--engine <name>|all`. Each engine gets one pass through the selected engine-backed stages. Images run only on the first pass because they use ComfyUI rather than the selected inference engine.

Within each stage, only one model is loaded at a time. `LlamaCppEngine` runs a model-specific llama-server process and restarts it whenever the requested model, context allocation, GPU mode, or concurrency shape changes. Each workload unloads or stops that model before advancing.

The selected keys are resolved through the fixed `STAGE_ORDER` registry in `orchestration.py`; a registered or selected key missing from that order is an error rather than a silently skipped stage. Each `StageDefinition` names its result section, selected-model count, runner, and only the preparation or cleanup hooks it actually needs. Native llama.cpp stages explicitly stop the HTTP engine, images restore normal engine mode before stopping it for ComfyUI, and ordinary stages have no special hooks.

The main JSON is owned by `ResultStore`, which atomically checkpoints when a run or stage changes state and after every model reaches a terminal outcome. Ctrl+C first records `interrupted`, then checkpoints again after workload `finally` callbacks flush their latest in-memory model data; the interrupted run is never relabeled complete. Unhandled stage-hook failures use the documented reasons `stage_preparation_failed`, `stage_execution_failed`, and `stage_cleanup_failed`; a cleanup failure secondary to a preparation or execution failure is retained in that stage's `cleanup_failure` metadata without replacing the primary reason. Final lifecycle teardown runs before terminal exception persistence, so a failed checkpoint cannot prevent server cleanup.

Stages currently end as `complete`, `failed`, or `interrupted`. The schema reserves `partial` for a future intentionally handled early-stop outcome; usable measurements retained before an unhandled failure remain visible through the failed stage's section and coverage counts rather than relabeling that stage partial.

The single-shot test builds an independent padded prompt for every measured call. Conversation instead grows one chat from a blank slate and samples it once at each eligible checkpoint, growing toward 128K and sampling through 96K, capped by the GGUF's real context ceiling. Growth uses larger steps while far from a checkpoint and finer steps within 8K, stopping at 99.5% of the target to avoid expensive tiny turns.

When single-shot and conversation are selected together, conversation excludes models with no usable single-shot result, a repeatable runner crash, a timeout at the first 512-token checkpoint, or a slow marker there. A deeper single-shot timeout alone does not exclude it. Conversation also stops after recording any sampled checkpoint below the slow-TPS cutoff. `--force-all` bypasses these speed gates, not actual failures. See [LLM workload](workloads.md#llm).

If `llamabench` is selected, the active inference engine's server is stopped entirely first (not just unloaded) to free memory. One prefill and one decode subprocess run the full matrix and all repetitions with the model retained; completed JSONL cases are checkpointed as they stream, so a timeout preserves every earlier case without reloading the model for every matrix cell. `llamabenchconc` likewise retains and checkpoints each JSONL row as it streams. One model's failure moves on rather than stopping the run — see [Workloads](workloads.md#llama-bench).

Each accuracy test warms a model, makes one deterministic first pass per question, scores it, and unloads the model. A literal length stop uses the remaining 40% of `--acc-token-budget` for one concise final-answer request; only that replacement is graded. Both passes share one `--acc-timeout` deadline. Token exhaustion, timeout, and periodic loop detection preserve and score the graded pass's partial output, record separate diagnostics, and continue the bank. MCQ and reasoning use confidence-ordered choice parsing so explicit final answers and later self-corrections take precedence over incidental reasoning text; reasoning deliberately disables MCQ's last-resort unstructured-letter fallback. Math accepts only completed scalar conclusions or same-clause results stated after `=`, while a leading numeric line must be corroborated by the response's final number or final completed equality result. Code answers run visible and hidden cases in one isolated Python subprocess, streaming per-test diagnostics so completed results survive a later timeout. Tool answers use `chat_tools` and require either exactly one matching call or a correct decline; question metadata can opt free-text arguments into limited normalization while identifiers remain exact.

Before images, the active inference engine is stopped entirely to free memory. ComfyUI is started only if it is not already reachable; processes managed by the benchmark are shut down after images or on exit, while a pre-existing external ComfyUI process is left running. Its loaded models and queue are still cleared during cleanup.

## Code organization

The implementation uses six broad package boundaries:

| Layer | Responsibility |
|---|---|
| `scripts/app/` | User entry points, public option handling, frontends, orchestration, and progress presentation |
| `scripts/runtime/` | Configuration, hardware discovery, engine adapters, shared execution helpers, and process controls |
| `scripts/workloads/` | One module per workload family plus model definitions, methodology profiles, and bundled test data |
| `scripts/results/` | Durable JSON/event storage, recovery, bundles, reports, policies, and diagnostics |
| `scripts/setup/` | Setup interfaces, system discovery/configuration, downloads, and archive safety |
| `scripts/release/` | Release manifests, scanning, SBOM/notices, maintenance, and readiness gates |

See [Project Structure](project-structure.md#scripts-in-detail) for the complete module-by-module map and [Engines](engines.md) for the adapter contract.

Versioned [workload packs](workload-packs.md) can name an ordered subset of these registered stages. The initial custom format is data-only; it cannot execute user-supplied code or redefine methodology.

Values that CLI flags can override at runtime (`RUN_TIMEOUT`, `ACC_TIMEOUT`, `ACC_TOKEN_BUDGET`, and `N_RUNS`) are read through dotted `config.*` lookups everywhere, rather than imported by name, so CLI assignments remain visible after import.

The frontend uses `Shared.plain_output`, native `cls` clearing on Windows, and ANSI clearing elsewhere, keeping selection prompts compact and untimestamped. It preserves the welcome banner through the initial single-engine test menu and the final model choices through confirmation, while clearing between screens and before subsequent redraws. The test menu keeps its number/range and group-shortcut legend on screen during every redraw; restored menus say which local state file supplied their selections and how to reset it. Benchmark execution output goes through `Shared.output` and the existing severity helpers, which prefix each independently emitted status or progress message with local `[HH:MM:SS]` time. This display layer does not touch result JSON, captured model responses, answer sidecars, caches, or generated artifacts.

## Configuration sources

The detailed workload shapes, checkpoints, model lists, and metrics live in [Workloads](workloads.md). Public flags and their effective defaults live in the [CLI Reference](cli-reference.md). Keeping those facts in one place prevents this architecture guide from becoming a second, stale parameter reference.

Runtime defaults are defined in `scripts/runtime/config.py`; model metadata is defined in `scripts/workloads/models.py`; the conversation checkpoint plan is defined by `LLMConversationBenchmark.CONV_CHECKPOINTS`; and dashboard context ordering is defined by `CTX_ORDER` in `dashboard/src/constants.js`. CLI-overridable values are read through `config.*` at use sites so an argument applied after import is still honored.

Material architecture changes are reviewed against the [architecture decision log](architecture-decisions.md) before implementation. Its simplicity gate requires a current reliability or customer need, explicit live-state ownership, compatibility evidence, and a deletion condition for every temporary path; speculative frameworks and unneeded service boundaries are not accepted.

Before creating `RunContext`, the CLI canonicalizes the selected engine, tests, stage order, safe model identities, and effective measurement settings into an immutable `RunPlan`. Unselected workload families have empty model lists, so an LLM-only run neither validates nor acquires identity from image or embedding models. Execution validation checks every resolved setting, types, ranges, unique positive sweep values, and nonempty family-appropriate identities for selected models: LLM, concurrency, and embedding entries carry catalog `tag` and `short`, while image entries use their catalog `short`. Validation completes before lifecycle preparation can start a runtime process, and the child repeats it after reconstructing the plan from SQLite. Its SHA-256 `plan_id` is deterministic for equivalent plans and changes when a measurement-affecting input changes. Schema-3 results embed that plan and identity while retaining the existing manifest fields for compatibility. Output and ComfyUI paths live in a separate `RunPaths` object and cannot enter the shareable plan; unknown configuration or model-identity fields are rejected rather than risking a secret or user path in exported metadata. `RunContext` carries only the values stage runners use: the plan, local paths, active engine, result store, and lifecycle coordinator.

When offline mode is selected, the parent installs its loopback-only socket policy before runtime discovery and every supervised Python runner reinstalls it from the immutable plan before executing a workload. Offline environment controls are inherited by native llama.cpp and ComfyUI processes. The plan and report record the setting so an offline run cannot share an execution identity with an otherwise identical online run.

New plans use run-plan schema 3 and declare the `sha256-v1` identity scheme. Each serialized plan instance carries a unique stable job ID, while `plan_id` deliberately excludes that value so independent executions of equivalent measurement semantics remain comparable. Stage, model, case, attempt, and sample identities form a job-scoped checked hierarchy beneath it. The plan also derives path-free identities for workload methodology, runtime adapter contract, privacy handling, retry behavior, timeouts, and result/event schemas; these join its existing model and resolved-configuration identity. Stage and model IDs can be created only for entities in the plan, while attempts and samples use positive one-based ordinals. Schema-1 and schema-2 plans remain readable without acquiring rewritten identities.

`event_store.py` defines the transactional storage boundary used by migrated workloads; atomic JSON remains the sole live source for each unmigrated section. The SQLite journal uses WAL with full synchronization, immutable job rows, append-only event triggers, checked parent identities and legal transitions, atomic event batches, and a SHA-256 digest chain. Job state and per-case coverage/numeric means rebuild solely from events; invalid samples remain recorded but excluded from projected means. A workload may adopt this store only when it stops writing the same live state through JSON and can reproduce its compatible export.

Single-shot LLM, conversation, native llama-bench, and both HTTP concurrency stages are journal-owned workloads. Their durable case, attempt, and sample state is written only to the sibling `results_name.events.sqlite3` journal; each JSON checkpoint is regenerated from its stage projection. Conversation commits a checkpoint as soon as the measured turn completes, including its observed depth, so a later growth timeout or interruption cannot erase shallower checkpoints. When single-shot ran first, the conversation child rebuilds that stage's projection and applies the same preflight selection rules before loading a model. Native llama-bench commits each streamed JSONL case and its internal repetition samples before reading the next row; it still uses exactly one prefill command and one decode command per model, so checkpointing never reloads the model per case. Concurrency keeps its contention semantics by retrying an entire implausible batch before committing only the final batch's request samples and batch-level throughput/memory fields. A workload may retain ephemeral values for immediate growth or slow-exit decisions, but neither those objects nor direct JSON mutations are authoritative. Other workloads continue to own their distinct sections in atomic JSON until migrated, so no individual stage has two live owners.

Safe resume compares the saved job's canonical plan ID, content hashes and sizes for every required model artifact and runtime binary, and methodology identities with a freshly discovered snapshot. Paths are never part of that snapshot. An exact match preserves completed cases, abandons any attempt left running by interruption, and assigns the next one-based attempt number to every remaining case. A changed identity, completed job, or journal case outside the current plan requires an explicit fork; no setting is silently updated in place. The journal persists the immutable resume snapshot with the job, but live resume remains unavailable until the first workload owns its case state there.

Recovery transitions are explicit journal events, not in-place edits. Completed and skipped cases cannot reopen; failed, interrupted, invalid, or timed-out cases may return to running only with a durable `resume`/`retry` marker, and a running attempt left by interruption becomes terminal before the next attempt number is allocated. Journal-backed execution hashes the selected local model and runtime bytes before the first stage and stores only size/SHA-256 identities, plus a digest of the execution profile so hardware, OS, or backend drift requires a fork. An ignored local `.resume_digest_cache.json` avoids rereading unchanged multi-gigabyte artifacts during ordinary new-run startup, but every inspect/resume/retry/fork decision bypasses that cache and re-hashes the current bytes. Paths and timestamps never enter the journal or portable result. Single-shot LLM can consume a prepared recovery allocation across the parent/runner process boundary: completed contexts are not rerun, prior attempts remain auditable, and only the latest attempt feeds its compatible aggregate.

`python -m scripts.results.recovery_inspector RESULT.json` is the read-only entry point for this boundary. It verifies the journal digest chain, recomputes current plan/model/runtime/environment identities, and reports `resume` or `fork`, exact mismatch reasons, stage states, case-state counts, retry-eligible case IDs/labels, and abandoned-attempt count without mutating the journal. Retry candidates are measured context/level cases in single-shot, conversation, or HTTP concurrency stages whose durable state is running, failed, interrupted, invalid, or timed out; completed/skipped evidence and model-level markers never appear as eligible. Native llama-bench retains whole-remaining-sweep resume because unstarted rows have no case identity to select. A portable result already marked complete always requires a fork even if an older journal lacks a terminal job event. A positive inspection is permission to offer recovery, not execution of recovery itself.

When recovery begins, JSON run/stage state returns to `running` through the narrow `ResultStore` API and the prior terminal status, timestamp, and reason move into append-only `recovery_history` records. The journal job likewise returns from a recoverable terminal state to running before stage work, including the edge where every stage committed before the original process stopped. Completed stages are never reopened. Normal execution, resume, retry, fork, failure, and interruption terminalize the journal job as well as JSON; portable JSON becomes complete only after the journal transition succeeds. This preserves why an earlier execution stopped without leaving either authority falsely terminal or running.

Progress events carry the engine currently running, and the graphical progress window renders one section set per engine in execution order, each heading naming its engine. A multi-engine run therefore reads top to bottom as it executes — every stage and model for the first engine, then the same again for the next — instead of the second pass overwriting the first's rows. Image generation appears once, under the first engine, matching where it actually runs.

Console output from the child runner is relayed verbatim rather than re-formatted: the runner already timestamps its own lines, so a second stamp would report when the parent relayed the line instead of when the event happened. Relayed text still passes through log redaction.

The parent supervisor prepares journal recovery before it starts the child runner. The retry marker and prior attempt are durable, so the child derives its next attempt from SQLite rather than inheriting process memory; failure between preparation and child start remains recoverable on the next invocation.

`python -m scripts.results.recovery_executor RESULT.json` performs state-changing recovery only when every saved stage is journal-owned. It repeats the inspector gate before mutation, retains run/stage terminal history, skips complete stages, resumes the interrupted stage, executes later journal stages in original plan order, checkpoints every projection, and terminalizes the original result. A plan containing embeddings, accuracy, images, or native batched concurrency is rejected before mutation until those legacy stages gain equivalent durable semantics.

The benchmark GUI exposes the same boundary in Result History. **Inspect Recovery** performs the read-only identity and journal check away from the interface thread; **Resume** repeats that check, shows the decision, asks for confirmation, and launches the recovery executor through the existing streamed log, progress, stop, and cleanup controls. **Retry Cases** lets the user choose eligible single-shot contexts, conversation turns, or measured HTTP-concurrency levels from one stage, reopens only those attempts, and leaves unselected evidence unchanged; failed attempts are selectable even when they produced no valid sample. The run remains failed with reason `selected_retry_has_remaining_cases` until no incomplete cases remain. **Fork** repeats the review, asks for a distinct output, and runs the immutable saved plan from the beginning under a new job/run identity while retaining source run, job, and plan IDs in `run.forked_from`; it refuses to overwrite either a result or journal. Journal-only plans use the direct fork executor. Plans containing embeddings, accuracy, images, or native batched concurrency are replayed through the normal benchmark path, which verifies the newly resolved plan ID exactly matches the source before creating output; this gives every workload a safe new-run fork without pretending aggregate JSON supports case-level resume. A user stop is recorded as interrupted, and unsupported in-place resume is explained before any result or journal mutation.

GUI-launched benchmark, resume, retry, and fork processes share one short-lived pause-control file under the OS temporary directory with their workload children, outside result discovery. The GUI enables pause controls only after the child starts, and removes the control file if launch fails. **Pause** takes effect at the next safe boundary before a measured request, conversation turn, image-generation run, concurrency level, native sweep command, or batched native model command; an in-flight case is allowed to finish and checkpoint first. The workload process and loaded model remain alive, the runner heartbeat continues, and no paused time enters a request measurement. Schema-4 results record timestamped pause-control transitions under `run.pause`, making the cache-cooling interval visible without treating it as measured latency. **Resume** releases the same boundary without changing the plan or completed evidence. Stop first releases a pause and then uses the normal interrupt/cleanup path; an interrupted process returns the conventional nonzero signal exit status so launchers cannot report it as successful. If the temporary control file disappears or becomes unreadable, workloads continue running at the next boundary instead of sacrificing a multi-hour run; the last checkpointed pause evidence remains available and the GUI control may no longer reflect execution state.

Large future event-owned artifacts use `ContentStore`, which streams bytes into an fsynced temporary file and addresses the final object only by full SHA-256. References contain digest, byte size, and media type—never a source filename or path. Existing objects are reverified before reuse, reads verify content and can enforce a caller size limit, and a failed replacement leaves no partial addressable object. The store is available to migrated workloads but does not copy current JSON sidecars or images yet.

The workload-runner boundary constructs one fixed internal Python entrypoint from a validated job ID, supported `llm`, `conv`, `llamabench`, `conc_tool`, or `conc_chat` stage, and absolute event-store path; callers cannot supply a command, executable, environment map, module, URL, or argument vector. The child reconstructs the immutable plan from SQLite, creates only the registered engine/tool internally, and owns its model processes and cleanup. Concurrency ladders, prompt sizes, and soft-exit floor come from that plan rather than mutable child defaults. A random ownership token travels only in the child environment and authenticates strict heartbeat, committed-event, and terminal envelopes. The parent starts an owned process group, measures heartbeat arrival on its own monotonic clock, rebuilds the affected JSON section after each commit notification, and on failure sends a graceful interrupt before bounded terminate/kill escalation against that owned group. A failed JSON export cannot roll back its preceding journal commit, while an interrupted SQLite transaction cannot damage earlier commits; both are recoverable by rebuilding the projection after restart. Other workloads remain in-process until they receive the same durable-state and parity coverage.

The graphical frontend can load either a standalone `RunPlan` JSON document or the plan embedded in CLI-created results. It maps the plan back to the same frontend state and public CLI command builder used for GUI-created runs, while retaining the current machine-local paths; unsupported developer-only values fail visibly instead of being dropped.

When the GUI supervises a run, the CLI emits opt-in structured stage, model, and measurement-quality events alongside the ordinary log. The always-on-top progress window shows queued/running/finished models, usable saved-result coverage, implausible-measurement retries and drops, combined benchmark-process CPU/RAM use, and an elapsed-rate remaining-time estimate that stays in a calibrating state until one model finishes. These events do not alter result files or terminal-only output.

Portable `.labresult` bundles contain canonical result JSON and optional content-addressed artifacts in a deterministic ZIP envelope. The manifest records SHA-256 and byte size for every payload. Verification rejects duplicate, undeclared, oversized, path-bearing, modified, non-finite, unsupported-plan, or locally unavailable methodology content and reproduces supported means and valid-run counts from raw samples before import. Imported artifacts retain their content-addressed bundle names, preventing archive paths or private source paths from controlling extraction.

Support bundles use a separate allowlist rather than redacting a copy of the full result. They contain application/runtime identity, non-identifying system fields, run/stage coverage, and structured diagnostic markers; hostname, model names, measurements, prompts, responses, raw logs, tokens, credentials, and source paths are not selected. Diagnostic strings receive an additional secret/path scrub. The GUI shows a scrollable list of every output file and leaf field and requires confirmation before writing the deterministic `.labsupport` archive.
